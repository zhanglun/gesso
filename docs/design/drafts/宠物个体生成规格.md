# 宠物个体生成规格 v1.0

> 状态：设计阶段草案；当前程序化占位层已接入 macOS 宠物窗口，正式资源尚未接入。本文定义首版程序化个体的输入、稳定性、候选身份和缓存边界；不定义最终美术稿，也不引入 AI 绘图。

## 1. 目标与非目标

### 目标

- 使用人工绘制的图层组件，按 root seed 稳定组合出猫或果冻个体。
- 同一组 `root_seed + species + generator_version + asset_version` 能稳定重建同一个个体。
- 每轮生成 3 个同物种、彼此不同的候选。
- root seed 通过命名空间子 seed 派生各字段；新增尾巴、毛色、衣服等字段时，不改变既有字段的生成结果。
- 候选确认前只存在于内存；确认时才创建正式 `pet_id`、存档、缓存和统计。
- 缓存损坏或生成失败时，可以使用同一 seed 重建，不更换个体身份。

### 非目标

- 不使用 AI 生成身体结构、骨骼、动作或任意新素材。
- 不允许候选直接写入正式宠物存档。
- 不在首版支持用户自由捏脸、外部宠物包、多宠物或普通流程换宠物。
- 不承诺无服务器条件下名字的全球绝对唯一。

## 2. 核心数据结构

### `SpeciesTemplate`

物种模板是人工维护的资源清单，不由 seed 创造新的结构：

```text
SpeciesTemplate {
  species_id: "cat" | "jelly",
  template_version,
  component_pools,
  palette_pool,
  marking_pool,
  face_pool,
  name_pairs,
  action_profile,
}
```

- `component_pools` 只列出已验证、已授权的组件 ID。
- `action_profile` 定义该物种适用的动作帧、节奏和表情范围。
- 猫与果冻可以共享动作语义，但不共享必须相同的帧和形变。

### `Candidate`

候选只在领养会话内存在；生成器返回的 `Candidate` 不含会话绑定的临时 `candidate_id`：

```text
Candidate {
  species_id,
  root_seed,
  appearance_params,
  name_pair: { zh, en },
  generation_signature,
  preview,
}
```

- 领养状态机在持有候选集时，可用会话 ID + reroll 轮次 + 候选序号派生临时 `candidate_id`；该 ID 不属于生成器结果，也不写正式存档。
- `preview` 可以是内存中的帧、绘制数据或临时 WebView 状态，不写正式缓存。
- 候选被关闭、重新抽取或退出后直接丢弃。

### `PetIndividual`

确认领养时才创建：

```text
PetIndividual {
  pet_id,             // 确认时生成的高熵 ID
  species_id,
  root_seed,
  appearance_params,
  name_pair: { zh, en },
  generator_version,
  asset_version,
  generation_signature,
  adopted_at,
}
```

`pet_id` 与 `root_seed` 都属于正式身份的一部分：缓存重建只能复用，不能重新生成。正式存档同时保存已经解析的 `appearance_params`；运行时优先使用已保存参数，不因组件池变化悄悄改变已领养个体。

`PetIndividual` 和 `PetSave` 已在 `gesso-core::pet_save` 实现为纯数据模型；`gesso-app::pet_store` 已实现安全读写和版本保护（BOM、校验、损坏备份、临时文件替换），并由 app 领养确认调用；`gesso-app::pet_cache` 已实现 macOS 优先的版本化临时目录和原子目录提交，领养确认先提交缓存再写存档，存档失败会回滚缓存。

### `PetCache`

缓存不是身份真源，存档才是：

```text
PetCache {
  pet_id,
  generator_version,
  asset_version,
  generation_signature,
  files,
}
```

缓存目录建议位于配置目录下的版本化路径，例如：

```text
pet-cache/<asset_version>/<pet_id>/
```

## 3. Seed 与生成流程

### 3.0 根 seed 与命名子 seed

`root_seed` 是个体的稳定来源，不作为一个按字段顺序消费的随机流。每个生成域使用固定命名空间派生自己的子 seed：

```text
root_seed
  ├─ adoption/candidate
  ├─ appearance/body
  ├─ appearance/face
  ├─ appearance/eyes
  ├─ appearance/coat_color
  ├─ appearance/marking
  ├─ appearance/tail
  ├─ appearance/clothes
  ├─ name
  └─ behavior/idle
```

实现约束：

- 新增字段只能追加新的命名空间，不得在旧字段前插入或重排随机消费顺序；
- 改变某个字段的选择规则，不得改变其他字段的子 seed；
- `root_seed` 只影响受约束的外观、名字和轻微表现参数，不决定物种、基础动作、点击反馈、碰撞区域、统计规则或核心玩法能力；
- 正式保存 `root_seed + appearance_params + generator_version + asset_version`，其中已解析参数是已领养外观的运行时真源；
- 新增尾巴、毛色、衣服等外观字段默认只影响新候选。已有宠物保持原样，除非未来明确执行存档迁移或用户主动换装。

### 3.1 候选生成

输入：

```text
selected_species
+ adoption_session_seed
+ reroll_generation
+ candidate_index (0..2)
+ generator_version
```

`adoption_session_seed` 只用于本次未确认领养会话；确认后将候选的 `root_seed` 保存为正式个体 seed。生成器本身不调用系统随机源。

通过版本化的稳定派生函数得到 3 个候选 seed。实现要求：

1. 三个候选 seed 不同；
2. 三个 `generation_signature` 不同；
3. 三个候选都属于已选物种；
4. 当前轮不能生成重复外观和名字组合；
5. 单次候选集内部最多尝试固定次数（例如 32 次）寻找不重复组合，超过后返回明确错误，不允许无限循环；
6. 新一轮默认不直接复用上一轮候选；
7. 生成失败可以重新派生 seed，但仍不能创建正式 `pet_id`。

reroll 不设用户可见次数上限。实现只允许一个生成任务在途：生成期间按钮 disabled，完成后再恢复；目标短冷却约 800ms–1s，以实际生成耗时为准。

### 3.2 外观组合

各字段使用自己的命名空间子 seed，从有限、已验证的组件池中选择参数；子 seed 只负责选择，不创建新结构。例如：

```text
appearance/body      → body_id
appearance/face      → face_id
appearance/eyes      → eye_id
appearance/coat_color → palette_id
appearance/marking   → marking_id
appearance/accent    → accent_id
behavior/idle        → idle_variant
```

未来新增 `appearance/tail` 或 `appearance/clothes` 时，只追加对应字段和资源池，不重排现有字段的派生路径。

root seed 派生出的子 seed 不得直接决定：

- 任意 SVG/位图内容；
- 未通过审核的动作骨骼；
- 超出模板边界的尺寸和碰撞区域；
- 外部网络资源。

### 3.3 名字生成

- `name_pair` 是一个不可拆分的中文/英文名字对；由 `name` 命名空间子 seed 选择，不能因新增外观字段而改变。
- 两种语言从同一个确定性名字记录产生，不在运行时分别随机。
- 名字从物种模板允许的名字池中选择；本机正式存档查重。
- 若正式确认时发生本机重名，使用同一 seed 派生的下一个允许名字对，不改变外观或 `pet_id`。
- 候选阶段不因为名字查重失败污染正式存档。

## 4. 领养确认与缓存事务

确认领养不应出现“存档成功但缓存半成品”或“缓存存在但没有正式身份”的可见中间态。当前 macOS app 已实现“候选确认 → 正式个体 → 版本化缓存元数据原子提交 → 安全存档”的事务骨架；缓存目录当前写入 `pet.json`，正式视觉资源生成尚未实现。完整缓存事务目标仍按以下语义处理：

1. 校验当前候选仍属于当前物种和领养会话；
2. 为本次确认生成正式高熵 `pet_id`，但先只存在于事务上下文；
3. 使用候选的 seed 和参数生成正式资源到临时目录；
4. 临时资源完整校验后原子改名为正式缓存目录；
5. 原子写入包含 `PetIndividual` 的存档；
6. 完成后才开始统计、显示宠物并关闭领养流程。

当前实现范围：app 目前执行第 1–5 步的最小事务路径；缓存目录内暂只写入 `pet.json` 元数据，正式视觉资源生成留待 macOS 宠物窗口阶段。

任一步骤失败：

- 保留当前候选和领养页；
- 删除临时目录；
- 不显示为已领养；
- 提供重试；
- 重试继续使用同一 seed 和候选参数，不能静默换个体。

如果正式 `pet_id` 已在事务上下文生成但事务失败，该 ID 丢弃；只有原子存档成功的 ID 才成为正式身份。

## 5. 重建、版本和损坏处理

- 缓存缺失、校验失败或版本不匹配时，未来优先使用存档中的 `appearance_params` 和版本信息重建；必要时用 `root_seed` 校验或补算，不得覆盖已保存参数。当前已实现版本化缓存目录和元数据提交，缓存重建器与视觉资源校验仍未实现。
- 重建不创建新 `pet_id`，不改变名字、统计和位置。
- 生成器或资源版本升级后，允许重建视觉缓存；是否需要存档迁移由版本迁移规则决定。
- 重建失败时保留存档，显示错误并使用已定义的静态占位/隐藏策略；禁止用空默认值覆盖正式个体。
- 存档损坏时沿用项目存档纪律：备份损坏文件、停止写入，不回写默认宠物。

## 6. 验收标准

- 相同版本、同一物种和同一 `root_seed` 能得到相同的外观参数、名字对和生成签名。
- 新增一个命名空间字段不会改变既有字段；已有宠物不因新增尾巴、毛色或衣服自动变样。
- 每轮 3 个候选的 root seed、签名和可见组合不重复。
- 候选阶段不存在正式 `pet_id`、正式统计和正式缓存目录。
- 确认失败后可以原候选重试；成功后 `pet_id`、root seed、解析后的外观参数和名字稳定保存。
- 删除缓存后可由存档中的解析参数重建；重建不改变正式身份。
- 名字查重只影响可选名字对，不影响已确认的外观和 seed。
- 生成器不访问网络，不读取外部宠物包，不调用 AI 服务。
